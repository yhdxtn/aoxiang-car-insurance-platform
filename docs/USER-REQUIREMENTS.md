# 车险报价小程序项目需求概要

> 本文根据两张白板照片、AI 投保助手界面示意图及补充说明整理，作为项目初步需求概要。未明确的业务规则、白板模糊字迹及佣金数字均标注为“待确认”，不作为最终开发规则。

## 1. 项目目标

建设一套车险报价与投保业务系统，包含：

- **微信小程序**：面向普通用户及各级代理，提供车辆分类、车险报价、订单、客户、政策、组织架构、积分等功能。
- **网页后台管理端**：供总部及各级代理进行业务、客户、订单、政策、组织架构、佣金和财务管理；按角色展示不同菜单和数据权限。
- **网页人工客服端**：供人工客服接待用户、查看报价会话、协助处理投保业务。
- **服务端与数据库**：后端采用 Java，数据库采用 MySQL。

## 2. 小程序整体结构

底部固定三个主导航：

1. **首页**
2. **订单**
3. **我的**

### 2.1 首页

首页提供车辆类型入口，用户选择车辆类型后进入对应的车险报价流程：

- 家用车
- 货车
- 摩托车

首页核心功能为**车险报价**。普通用户也可以进入报价流程，不要求必须是代理角色。

> 车辆类型均纳入产品规划。白板另有货车接口对接进度、摩托车业务暂缓/方案待确认等记录，具体承保渠道及上线顺序需进一步确认。

### 2.2 订单

订单页面展示当前登录账号权限范围内的订单，并根据角色提供相应订单管理能力。需支持订单列表、订单详情及状态跟踪。

建议订单信息至少关联：客户、车辆、报价方案、保单/投保信息、所属代理层级、创建人及订单状态。具体字段和状态流转待业务确认。

### 2.3 我的

展示当前用户的个人及业务信息，初步包括：

- 个人资料及账号信息
- 当前角色、所属组织/上级代理
- **积分余额**及积分明细
- 积分商品兑换入口（白板内容，兑换商品和规则待确认）
- **政策查看**：查看当前角色可见、适用的车险政策
- **组织架构查看**：查看权限范围内的组织/上下级关系
- 佣金等级、业绩等个人业务数据（白板提及，具体展示口径待确认）

## 3. AI 投保助手 / 车险报价流程

报价页面采用类似聊天机器人的对话式交互，参考所提供的“AI 投保助手”界面。

### 3.1 页面流程

页面顶部展示投保步骤：

1. 资料确认
2. 方案报价
3. 投保确认

同时显示当前办理业务，例如“车险投保”。

### 3.2 资料采集与识别

- AI 助手引导用户提交车辆资料。
- 支持**上传行驶证照片**，由系统识别车辆信息。
- 支持**手动填写**，作为无法上传或识别失败时的补充方式。
- 上传后在聊天窗口展示已上传文件及文件名。
- 识别完成后，将车辆信息以卡片形式展示，供用户核对。
- 用户可选择“修改信息”或“确认并继续”。

示意图中的车辆信息字段包括：

- 车牌号
- 车辆类型
- 使用性质（示例为家庭自用）

实际识别字段可根据承保及报价接口要求扩展，例如车辆品牌型号、注册日期、车架号、发动机号、座位数等，具体以业务确认及接口能力为准。

### 3.3 方案报价

- 资料确认后进入方案报价步骤。
- 系统根据车辆信息、所选车辆类型、适用政策及保险公司/渠道接口获取报价方案。
- 展示可选方案及保费、险种、保障内容等信息（具体展示字段待确认）。
- 用户选择方案后进入投保确认。

### 3.4 投保确认

- 展示最终投保资料及所选方案。
- 用户确认后提交投保申请或进入后续人工处理流程。
- 记录报价、确认及投保过程，便于订单查询和客服跟进。

### 3.5 聊天交互能力

- 支持文字输入、图片/资料上传及消息发送。
- AI 助手按步骤提示用户补充资料、核对信息和选择方案。
- 支持人工客服介入或转接；人工客服通过网页端处理会话。
- 保存会话记录、上传资料、识别结果及操作轨迹。

## 4. 用户角色与组织架构

系统采用多级代理组织架构和基于角色的数据权限控制。初步角色包括：

| 角色 | 主要定位 | 初步权限 |
|---|---|---|
| 总部 | 平台及业务管理方 | 制定总政策、管理代理体系、查看全局业务数据、管理订单及财务规则 |
| 总部管理员 | 总部后台管理角色 | 账号、角色、组织、系统配置及业务管理；具体权限由总部配置 |
| 总部财务 | 总部财务角色 | 查看财务相关数据、佣金/结算/对账等；不默认拥有系统管理权限 |
| 一级代理 | 总部下级代理 | 查看权限范围内客户和订单；接收总部政策，并按规则向下配置二级代理政策 |
| 二级代理 | 一级代理下级代理 | 查看自身及授权范围内客户和订单；接收上级政策 |
| 普通用户 | 非代理用户 | 可使用小程序进行车险报价、资料提交及查看本人订单 |
| 人工客服 | 客服工作角色 | 通过网页客服端处理用户咨询、报价会话及投保协助；数据范围按授权配置 |

组织层级应支持后续扩展更多代理级别（补充说明中有“等”）。具体是否固定为总部、一级、二级，或允许继续向下发展，待确认。

### 4.1 政策逐级配置关系

政策采用逐级管理机制：

1. **总部制定总政策**，作为平台/业务基础政策。
2. 总部向一级代理配置或下发适用政策。
3. 一级代理在总部授权范围及规则约束下，向其下属二级代理配置政策。
4. 二级代理执行上级下发的政策，不得超越上级授权范围。
5. 系统应保留政策版本、适用范围、生效时间、创建人、修改记录及上下级来源，便于追溯。

政策的可调整项目、代理可调整幅度、审批机制及政策冲突处理规则需进一步确认。

### 4.2 数据权限原则

- 总部可查看和管理全平台数据。
- 一级代理仅查看自身及下级授权范围内的数据。
- 二级代理仅查看自身及下级授权范围内的数据。
- 普通用户仅查看本人资料、报价及订单。
- 总部管理员、财务、客服等总部内部岗位按职责分配菜单、操作和数据权限。
- 关键操作（政策调整、订单处理、佣金调整、财务操作、用户权限变更）应记录操作日志。

## 5. 业务管理功能

### 5.1 客户管理

- 客户资料新增、查看、编辑及维护。
- 客户与车辆、报价、订单及所属代理关系关联。
- 按角色和组织范围控制客户数据可见范围。
- 支持客户信息查询及跟进记录（具体字段和跟进流程待确认）。

### 5.2 订单管理

- 订单列表、详情、状态及业务记录。
- 根据角色展示本人、下级或全平台订单。
- 订单与客户、车辆、报价方案、保单信息及代理组织关联。
- 支持订单查询、筛选及统计。

白板中的查询功能可辨认出以下查询维度，需业务确认后确定为正式字段：

- 车牌号
- 姓名/客户姓名
- 车架号
- 保单号

### 5.3 政策管理

- 总部制定和维护总政策。
- 总部向一级代理下发政策。
- 一级代理按授权向二级代理配置政策。
- 各级查看当前生效政策及历史版本。
- 政策与车辆类型、保险公司/渠道、险种或业务范围的匹配规则待确认。

### 5.4 组织架构管理

- 建立总部、一级代理、二级代理等上下级关系。
- 支持代理账号创建、归属、启停用及调整。
- 展示组织树及各级代理信息。
- 组织关系变更需记录历史，避免影响历史订单和佣金归属。

### 5.5 业绩统计与佣金

- 白板提及订单管理关联**统计业绩**。
- 可按角色及组织层级统计个人、代理及下级团队业绩。
- 佣金规则与政策、订单、代理层级关联。
- 我的页面可展示个人佣金等级/业绩信息；后台可供有权限人员查看统计结果。

早期白板记录了一级、二级、三级档位，以及 90万、80万、60万、50万、40万、30万、20万、10万、0万等金额，另有 0.3%、0.4% 等比例及若干金额数字。由于原图箭头关系和文字不清晰，**这些仅作为待核实的讨论记录，不纳入已确定的佣金计算规则**。

### 5.6 积分管理

- 小程序“我的”页面展示积分余额。
- 支持积分明细查询。
- 白板提及商品兑换，需确认是否纳入首期范围，以及积分获取、扣减、兑换和商品管理规则。

## 6. 网页端系统

### 6.1 后台管理端

后台按角色展示不同菜单、功能和数据范围，初步包括：

- 总部管理工作台
- 总部管理员管理
- 总部财务管理
- 一级代理管理端
- 二级代理管理端
- 客户管理
- 订单管理及查询
- 政策管理与逐级下发
- 组织架构管理
- 业绩统计与佣金管理
- 积分及兑换管理（是否首期上线待确认）
- 用户、角色、菜单、权限及操作日志管理

### 6.2 人工客服网页端

- 客服登录及权限控制。
- 查看待接入/进行中的用户会话。
- 与小程序用户进行文字沟通。
- 查看用户提交的行驶证等资料、车辆识别信息和报价进度。
- 协助用户补充资料、核对车辆信息、跟进报价及投保。
- 支持会话转接、处理状态及历史记录（具体客服流程待确认）。

## 7. 技术方案与系统组成

| 层次 | 初步方案 |
|---|---|
| 用户端 | 微信小程序 |
| 管理端 | Web 网页后台 |
| 客服端 | Web 人工客服工作台 |
| 后端 | Java |
| 数据库 | MySQL |
| 外部对接 | 车险报价/投保相关保险公司或渠道接口；车辆资料识别能力 |

建议后端按模块划分：用户与认证、角色权限、组织架构、客户、车辆资料、报价、投保订单、政策、业绩佣金、积分、客服会话、文件资料及操作日志。实际技术框架、部署方式、缓存/消息组件和接口供应商待技术设计阶段确定。

## 8. 当前进度与白板事项

根据第二张白板可辨认内容，初步记录如下：

- 小程序：提出“加快开发”，应优先推进小程序核心流程。
- 车险：有“接口对接进度”的记录，需跟进报价/投保接口联调。
- 货车：涉及接口对接进度，具体进度及可用渠道待确认。
- 摩托车：白板出现“暂停”及方案/承保问题相关备注，具体原因和恢复条件字迹不清，需确认是否暂缓上线。
- 小程序入口：按车辆种类分类。
- 订单管理：关联业绩统计及订单查询。
- 查询字段：车牌、姓名、车架号、保单号等（部分字迹需确认）。

## 9. 建议的首期开发范围

为尽快形成可用闭环，首期可优先实现：

1. 小程序首页车辆分类入口（家用车优先，货车/摩托车按接口准备情况分阶段开放）。
2. AI 投保助手聊天界面、行驶证上传、信息识别、手动填写和资料确认。
3. 车险报价方案展示及投保确认流程（依赖保险接口）。
4. 用户登录及总部、一级代理、二级代理、普通用户的角色权限。
5. 小程序订单列表及订单详情。
6. 后台客户管理、订单管理、政策管理和组织架构管理。
7. 总部向一级、一级向二级逐级配置政策的基础能力。
8. 人工客服网页端及会话接入能力。

积分兑换、复杂佣金档位、更多代理层级及摩托车/货车特殊承保流程，可在规则和接口明确后分阶段实施。

10. 报价、投保申请、支付、出单、退保/批改等订单状态和流程如何定义？
11. 人工客服是否需要主动分配会话、转接、工作量统计及服务评价？
12. 货车接口对接当前进度如何？摩托车是否暂缓，具体承保问题是什么？
13. 订单查询字段最终确定为车牌号、客户姓名、车架号、保单号，是否还需手机号、订单号等？
